# hrt protocol — developer guide

**Audience:** the five-person implementation team. This is the working
contract for the raw server, the CLI client, the web approval flow, and the
optional F2F/GPG service. The rationale and threat model are in
[`../superpowers/specs/2026-10-20-hrt-pairing-transport-design.md`](../superpowers/specs/2026-10-20-hrt-pairing-transport-design.md).
If the two disagree, this guide wins for wire details and the design doc wins
for security intent.

## 1. Component boundaries

```
hrt-tool (C++ CLI) ── raw TLS 1.3 / mTLS ── hrt-raw-server (Node/TS)
                                                │ loopback service token
                                                ▼
                                      existing web app (workerd + D1)
                                                │
                                                ▼
                                      account / pairing / hold data

F2F/GPG service (separate advanced component)
  users' public keys + cohort seats + optional escrow key
  never part of hrt-tool's default backup path
```

- `hrt-raw-server` is an adapter: TLS, device certificates, framing, and a
  strict allowlist to `/api/tool/v1/*`. It stores no account data.
- The web app owns accounts, pairing requests, devices, holds, trusted IPs,
  and the 12-hour request history.
- The F2F/GPG component is isolated. It must not share private keys, code
  paths, or default encryption with `hrt-tool` or `hrt-cold`.

## 2. Transport

- TLS 1.3 (not SSL; SSL/TLS 1.0/1.1 are obsolete) on a dedicated port,
  default `9443`.
- ALPN: `hrt/1`.
- Server certificate: generated by the operator or the raw server at first
  start; the CLI pins its SPKI SHA-256 on first contact. No public CA is
  required for the raw transport, but pinning is mandatory.
- Client certificate: not required for `pair.start` / `pair.poll`; required
  for every other frame. The CLI generates a random key pair and a
  self-signed certificate on first pairing, sends the certificate in the
  `pair.start` body, and stores the private key and certificate in the
  encrypted vault. The web app records the SHA-256 DER fingerprint when it
  approves the request; the raw server compares the certificate presented
  on each connection with that registry. No device CA is needed.
- The server certificate lives in the persistent volume with the private
  key mode 0600. There is no server-side device CA; revocation is a web-app
  state change and is enforced by the authorize call.
- Proxies: the CLI uses `socks5h://` only; target names are never resolved
  locally. The proxy's own host should be an IP or loopback.

## 3. Framing

Each frame:

```
u32 big-endian length (1 .. 25,165,824)
JSON object (UTF-8)
```

The 24 MiB cap accommodates the web API's 16 MiB JSON body after base64
expansion (4/3) plus envelope overhead. The server bounds concurrent
connections separately so the cap cannot multiply into unbounded memory.
There is no compression and no pipelining. A connection is
request/response; the client may send the next frame after reading the
response. Request ids are client-generated and echoed; duplicate ids within
a connection are rejected. Idle timeout: 30 seconds; handshake timeout: 15
seconds; a frame that exceeds the limit closes the connection.

Common envelope:

```json
{ "id": "c-1", "op": "request", "method": "GET", "path": "/api/tool/v1/snapshot",
  "headers": {"authorization": "Bearer ...", "accept": "application/json"},
  "body_base64": "" }
```

Response:

```json
{ "id": "c-1", "status": 200, "headers": {"content-type": "application/json"},
  "body_base64": "..." }
```

Errors that are not an HTTP response:

```json
{ "id": "c-1", "error": { "code": "FRAME_TOO_LARGE", "message": "..." } }
```

Stable error codes: `BAD_FRAME`, `FRAME_TOO_LARGE`, `UNKNOWN_OP`,
`NOT_AUTHORIZED`, `CERT_REQUIRED`, `CERT_INVALID`, `PATH_NOT_ALLOWED`,
`SERVICE_UNAVAILABLE`, `RATE_LIMITED`, `PAIRING_HELD`.

## 4. Operations

| op | client cert | purpose |
| --- | --- | --- |
| `pair.start` | no | begin a device pairing request; sends username, code SHA-256, self-signed device certificate, device name, client version |
| `pair.poll` | no | poll with request id + poll secret; returns pending / approved / denied / expired (a held request stays indistinguishable from pending) |
| `pair.deny` | web only | web-side denial (not a raw op) |
| `request` | yes | forward an allowlisted HTTP request to the web app |
| `ping` | optional | liveness; returns server time and protocol version |

`request` allowlist:

- path prefix `/api/tool/v1/`;
- methods `GET`, `POST`, `PUT`, `DELETE`;
- request headers: `authorization`, `accept`, `content-type`, `if-match`;
- request body limit 16 MiB (the web API's own limit);
- response headers pass through except hop-by-hop headers;
- the raw server never reads or transforms health payloads.

Any other path returns `PATH_NOT_ALLOWED` and is audited without the body.

## 5. Pairing sequence

```
CLI                         raw server                    web app / web user
 |-- pair.start (code hash, pubkey) ->|                          |
 |                                   |-- POST /hrt/pair/start -->|
 |                                   |   (service token, IP)     |
 |<-- request id, poll secret, url --|                          |
 |                                   |                          |-- owner opens
 |                                   |                          |   Account/Security
 |                                   |<-- GET pending ----------|
 |                                   |<-- approve + code -------|
 |                                   |-- verify hash, mark ----->|
 |-- pair.poll --------------------->|                          |
 |                                   |-- status --------------->|
 |<-- approved, token, user id ------|                          |
 |   (cert fingerprint registered)   |                          |
 |-- later: mTLS + request frames -->|-- HTTP /api/tool/v1/* -->|
```

Rules:

- The CLI generates 64 random bytes with `RAND_bytes`, prints 128 lowercase
  hex characters, and keeps them in memory. Only SHA-256 is sent.
- `pair.start` includes the lowercase username the CLI is trying to sign in
  as. The service associates pending requests and abuse counters with that
  name so the account owner sees only their own requests and the one-hour
  hold can target the spammed account. The response never says whether the
  account exists.
- The web page shows the server-observed IP, country when the deployment
  has a local GeoIP source, device label, certificate fingerprint, and time.
- Approval requires the code and a web session whose username matches the
  request; adding a trusted IP additionally requires the web account
  password.
- The poll secret is independent of the code and is not displayed. It is
  stored as a hash, like the code.
- The token is returned only after the code hash matches and the web
  approval exists. It is bound to the account, origin, and device
  certificate fingerprint.
- A wrong code, denial, expiry, or hold returns a uniform failure; a held
  request is indistinguishable from a pending one until it expires, so the
  attacker cannot learn that the account is in a hold.
- The CLI's local 60-second login-failure pause applies to repeated pairing
  failures. The server's rate limits remain authoritative.

## 6. Certificate lifecycle

- Raw server certificate: generated at first enable; pin displayed to the
  operator; rotation requires re-trust (`--trust-server`) like HTTPS.
- Device identity: the CLI generates a random key pair and self-signed
  certificate on first pairing. It uploads only the certificate in
  `pair.start`; the private key stays in the encrypted vault. The web app
  computes and stores the SHA-256 DER fingerprint when it approves the
  request. No device CA or server-signed certificate is used.
- Request authorization: the raw server computes the presented
  certificate's fingerprint and asks the web app
  (`/api/tool/v1/hrt/device/authorize`) whether that fingerprint belongs
  to an active, non-revoked device for the account. The positive answer is
  cached briefly (default 10 seconds) and re-checked after that.
- Rotation: generate a new key pair/certificate, pair it again, and revoke
  the old device. The old certificate stops authorizing immediately after
  the web state changes and the cache expires.
- Revocation: `revoked_at` in the web app is authoritative; a CRL is not
  needed. A revoked device gets `NOT_AUTHORIZED`, never a token.
- Private keys: CLI device key generated with OpenSSL; stored only in the
  encrypted vault; never uploaded; zeroized on logout if the user chooses
  not to keep the device.
- No hardware identifiers. The device key is random and per install.

## 7. Web API (additive; existing auth untouched)

Service-token endpoints (loopback only, `X-HRT-Service` token from a 0600
file; unavailable on Cloudflare):

- `POST /api/tool/v1/hrt/pair/start`
- `POST /api/tool/v1/hrt/pair/status`
- `POST /api/tool/v1/hrt/device/heartbeat`
- `POST /api/tool/v1/hrt/request/authorize` (optional, for per-request
  device/token checks)

Web-session endpoints (existing session + CSRF):

- `GET /api/hrt/status` — hold, blocked count, expiry, password advice.
- `GET /api/hrt/requests?since=12h` — recent requests.
- `POST /api/hrt/requests/:id/approve` — code + optional trusted IP.
- `POST /api/hrt/requests/:id/deny`.
- `GET|POST|DELETE /api/hrt/trusted-ips` — add/remove requires password
  re-entry; masked display.
- `GET /api/hrt/devices`; `POST /api/hrt/devices/:id/revoke`.

The raw server calls the first group with the service token and forwards
the authoritative client IP in `X-HRT-Client-IP`. The web app ignores
client-supplied forwarding headers. The web app's `/version` advertises
`hrt` only when the operator enabled both the raw server and the web flag.

## 8. Data model and retention

| Table | Key fields | Retention |
| --- | --- | --- |
| `hrt_pair_requests` | id, account, device key id, code hash, encrypted IP, country, status, timestamps | 12 h; code hash deleted on approval/expiry |
| `hrt_devices` | account, key id, label, created, last seen, expires, revoked | revoked/unused expiry (default 90 d) |
| `hrt_holds` | account, hold until, blocked count, first/last blocked | 1 h hold, ≤24 h aggregate |
| `hrt_trusted_ips` | account, encrypted address/prefix, label, created, last used | until removed or 90 d |
| rate-limit counters | HMAC(IP), window, count | window only |

No raw IP logs, no codes, no hardware identifiers, no third-party GeoIP.
The web UI reads only the authenticated account's rows.

## 9. F2F / GPG service (separate advanced component)

This service is deliberately not part of `hrt-tool`'s default backup
path. It serves the face-to-face network where members verify each other's
fingerprints out of band.

### 9.1 Trust model

- Every user generates their **own** OpenPGP key pair on the client. The
  private key never leaves the client and is stored encrypted under the
  user's passphrase/vault. The public key is uploaded to the service.
- Data sent to a user is encrypted to that user's public key (and, if the
  deployment enables escrow, also to the cohort escrow key). Users cannot
  decrypt each other's copies. The public key is for encryption/verification;
  decryption/signing needs the private key.
- If escrow is enabled, the server holds a cohort private key and can read
  the escrowed copy. This is a managed mode, not end-to-end confidentiality
  against the server; it must be opt-in and labelled.
- TLS 1.3 protects the transport. It does **not** protect a private key that
  has already leaked; key rotation, revocation, and encrypted-at-rest
  storage do that. Never call SSL/TLS a substitute for key hygiene.

### 9.2 Cohorts and seats

- A cohort ("bus") has exactly 100 seats, numbered 1..100.
- Each cohort has one GPG keyring of member public keys and, if enabled,
  one escrow key pair.
- A new user takes the lowest free seat. When all 100 seats are assigned,
  the cohort becomes `full` and the next user starts a new cohort/keyring.
- A deleted account's seat becomes `deleted` and is **never reused**. This
  prevents identity/key confusion; holes are expected.
- Cohort states: `active` → `full` → `retired` (no new encryption) →
  `revoked` (compromise) / `archived` (decrypt-only) → `deleted`.
- Old cohorts remain available for decryption until archived/deleted. A
  ciphertext must carry `cohort_id`/`key_id` so clients can find the right
  key.

### 9.3 Key lifecycle

1. User generates a key pair client-side; uploads the armored public key and
   confirms the fingerprint out of band with peers.
2. The service stores the public key in the active cohort's keyring; the
   user's private key remains local.
3. The user may rotate: generate a new key pair, upload the new public key,
   keep the old private key for old ciphertext, and mark the old public key
   `retired`.
4. A cohort that is full stops accepting new keys; a new cohort is created.
5. A cohort with no member activity for 180 days is **retired**
   (no new encryption), revoked if compromised, and archived for
   decryption. Deletion of the escrow private key happens only after a
   longer retention and a check that no live ciphertext depends on it; the
   operator may export/notify first. A seat tombstone remains even if the
   key is deleted.
6. Revocation publishes a revocation certificate; clients pin fingerprints
   and warn on change. The service never treats a changed fingerprint as a
   silent replacement.

### 9.4 Storage and operations

- Private keys (escrow only) encrypted at rest with a service key; access
  audited; zeroized on delete; backups encrypted.
- Public keyrings are public data but still integrity-checked.
- 180-day and deletion jobs are scheduled; no per-message content is
  retained for activity accounting—use coarse `last_used_at`.
- The F2F service and `hrt-tool` do not share keyrings or private keys.

## 10. Anti-abuse, in brief

- Account-level 1-hour hold on hrt login spam; hrt requests are black-holed
  with indistinguishable responses; web login and existing tokens are
  unaffected.
- No global IP bans; no VM detection; no hardware fingerprints.
- Trusted IPs are user-managed, password-re-authenticated, encrypted, and
  only exempt the hold—not authentication.
- Exact thresholds are server configuration, not public documentation.
  Secrets are not a security boundary: the behavior must be safe if known.

## 11. Deployment and compatibility

- `HRT_RAW_ENABLED=0` by default. Enabling requires the raw server, its
  server certificate/key, and a service token; the web capability and the
  raw server must agree. Client certificates are self-signed per device and
  registered by SHA-256 fingerprint at pairing; there is no device CA.
- Docker runs the web app and raw server as separate processes on one
  volume; expose only the raw TLS port and the web port as intended.
- `hrt://` is unavailable on Cloudflare Workers/Pages, Vercel Edge, Netlify
  Edge, Deno Deploy, Lambda@Edge, Fastly Compute@Edge, and static hosting.
  Those deployments keep the HTTPS API; the CLI warns on every HTTPS login
  that the transport terminates at the server or its CDN.
- HTTPS fallback is the legacy password login, not web-approval pairing. The
  warning (printed every HTTPS login) is:

> warning: HTTPS terminates at the server (and any CDN in front of it); this
> transport is not end-to-end encrypted. Use an hrt:// server when the
> deployment offers one.

  `hrt-tool login --require-hrt` refuses any non-`hrt://` server.

## 12. Test checklist

- Frame: length bounds, bad JSON, unknown op, duplicate id, timeout,
  oversized body, path/method/header allowlist.
- TLS: server pin, wrong pin, missing client cert, invalid/revoked cert,
  expired cert, CA isolation.
- Pairing: hash-only storage, TTL, single use, wrong code, replay, denial,
  expiry, hold, poll-secret separation, token/device binding.
- Web: CSRF, session required, password re-auth for trusted IPs, masked
  display, 12-hour cleanup, no code/hash exposure.
- Abuse: hold triggers/expiry, uniform responses, no state change, old
  tokens/web login unaffected, trusted-IP spoofed header rejected.
- F2F/GPG: client-side key generation, public-key-only upload, per-user
  decryption, cross-user decryption impossible, cohort-full rotation,
  seat tombstone, 180-day retire/archive, revocation, deleted-key
  behavior, wrong/tampered/replayed ciphertext.
- Data: retention jobs, no plaintext IP/code/private key in logs or DB,
  zeroization, backup/restore.

## 13. Open implementation decisions

- Exact token lifetime and whether the raw transport uses short-lived
  device certificates plus token refresh.
- Whether the web app checks the device state per request or the raw server
  caches it briefly.
- The 180-day grace/archive duration and notification channel (no content
  retention).
- OpenPGP library/sidecar choice for the F2F service (vetted, licence
  compatible).
